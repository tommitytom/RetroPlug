# Phase E4: TypeScript nodes on the box, on MicroQuickJS

**Date:** 2026-11-06 · **Branch:** `feature/modularize` · **Status:** designed (on e7bdd3736, merged as e91f055a5)

Phase E is the Pico runtime ([modular-graph-phase-e1-design.md](modular-graph-phase-e1-design.md) section 3). E1 made a
C++ node's source build for the RP2350, E2 put the first pack behind the package boundary, and E3 made a graph run on
the box: the desktop exports a plan as a blob, the firmware loads it into a static arena, and the box's bridge is a
built-in plan ([modular-graph-phase-e3-design.md](modular-graph-phase-e3-design.md)). E4 lets a TypeScript node run in
that plan beside the C++ ones, on MicroQuickJS (mquickjs), and moves BlipToaster's MIDI policy into such a node. E1 set
its gate: a TS node in the box's MIDI path on the rig.

## 1. Before E4

- **mquickjs is not on this branch.** Bellard's MicroQuickJS (pinned at 6d4d7eb) is used on the unmerged
  `feature/launchpad` branch, whose `check:portable` bundles the Launchpad core, lowers it to ES5, scans for library
  calls the engine lacks and runs it under Node and `mqjs` for byte-identical transcripts. The engine runs in one
  caller-supplied buffer with a compacting garbage collector and no malloc; its JavaScript is ES5 plus typed arrays,
  `ArrayBuffer`, JSON, RegExp and closures, and lacks Map, Set, Symbol, Proxy, Promise, BigInt and most ES2015 library
  calls. It compiles bytecode ahead of time (`mqjs -o`, `-m32` for a 32-bit target), which runs without verification,
  so only trusted bytecode may run. Its C functions live in a stdlib table compiled to C structures by its build tool.
  Its README gives about 100 KB of Thumb-2 code and a heap from 10 kB; nothing has been measured on the RP2350.
- **TS nodes run only on the desktop, in full QuickJS.** The script host (`packages/native/src/host/script/ScriptHost`,
  B3a and C1) gives each pack a pair of runtimes, reads settings as JSON only and answers no interfaces, so `exportPlan`
  refuses a script node (`settings-export`). Its block API relies on Promise jobs, Proxy, a frozen prototype and
  `ArrayBuffer.transfer`.
- **`defineNode` is not portable.** It uses Set, `includes`, `find`, `Object.entries`, `startsWith`, `endsWith` and
  `Number.isInteger` (spec/07 records it).
- **The box runs from RAM.** E3's image takes about 305 KiB of the RP2350's 512 KiB SRAM under `copy_to_ram`, which is
  what holds E2's latency; the 128 KiB arena holds the bridge plan's 30 KiB.

## 2. Decisions taken

The user's, in order (2026-11-06; the Phase E list is `.superpowers/e-pico/decisions.md`):

1. **Purpose: MIDI- and event-rate logic.** TS nodes on the box transform, route and generate events, and hold a
   cart's policy; audio-rate DSP stays C++. Box control logic may become nodes later.
2. **One engine per pack wherever it runs.** A pack marked for the device runs on mquickjs on the desktop as well, in a
   second, small script host beside the QuickJS one, so the desktop runs the engine and the source the box runs.
   Desktop-only packs stay on QuickJS.
3. **Packs are built into the firmware.** Each pack the box lists is compiled at the firmware's build, TypeScript to
   ES5 to mquickjs bytecode, and embedded beside the exported plan; the box registers its types at boot and the blob
   names script types by id. The blob's format does not change, and the bytecode is trusted because only the build
   makes it.
4. **Everything runs from RAM.** mquickjs and the bytecode run from SRAM like the rest of the image, so latency holds;
   the arena shrinks toward what the box's plans need to make room. Moving cold code back to flash is the reserve lever
   if the measured figures do not fit.
5. **One context per pack.** Each pack's manifest declares its heap; the exporter and the loader size and place it like
   everything else, and refuse a plan that does not fit, naming the pack. A heap that runs out, a throw or a deadline
   overrun silences only that pack's nodes.
6. **One `defineNode`, made portable.** The same API serves every pack. For a pack marked for the device, the
   definition refuses audio ports and anything asynchronous.
7. **BlipToaster's policy becomes a TS pack.** A small `bliptoaster` pack holds the cart's MIDI policy and replaces
   `rp.core.midi-filter` in the box's plan; the C++ filter stays in `rp.core` for every other use.

## 3. The shape

| Piece | Where | Built for |
|---|---|---|
| mquickjs at 6d4d7eb, with its stdlib table generated by its build tool | `deps/mquickjs` (vendored or a submodule: the prototype decides) | desktop and device |
| The device-pack toolchain: bundle, lower to ES5, scan, compile to bytecode | `packages/retroplug/scripts` and CMake | desktop, at build time |
| `defineNode` and its helpers in the mquickjs subset, with the device-pack checks | `packages/retroplug/src/graph` | both engines |
| The mquickjs script host | a portable library beside the desktop's `ScriptHost` | desktop and device |
| Package-level memory | the node SDK (`rp_package`) and the loader | desktop and device |
| The `bliptoaster` pack and its policy node | `packages/bliptoaster` | desktop and device |
| The box: packs embedded and registered, the arena trimmed, the new plan | `pico/n8-host`, `pico/host` | device |

At build time a device pack's TypeScript becomes bytecode, which the box embeds beside its plan (built into flash and
copied to RAM with the image). At boot the box registers each pack's node types beside the C++ ones; the loader sizes
and places each pack's heap and every node's state in the arena; each block, the executor calls a script node through
the same C ABI as any node, and the host runs its `process(block)` in its pack's context under a deadline. On the
desktop a device pack goes through the same toolchain and the same host, so the exporter's trial load and the
device-mode tests run real script nodes.

## 4. The mquickjs script host

**Registration.** A pack's bytecode, run once, defines its nodes with `defineNode`. The host makes one `rp_node_type`
per definition in one `rp_package` per pack: the type id from the definition, `query_memory` the node's native shim,
and the pack's heap declared once at package level (section 5). The box does this at boot, before the plan loads.

**Settings.** The desktop's mquickjs host answers `rp.sdk.settings-json/1` with a node's parsed settings, so `exportPlan`
writes them as msgpack as it does for a C++ node. On the device the host decodes the msgpack into a JS object and hands
it to `create()`; the export applied the defaults. A node whose ports follow its settings computes them from the same
code on both sides.

**The block API** is today's: `messages()`, `send()`, `control()`, `emit()`, `frames` and `transport`, implemented as
C functions in mquickjs's stdlib table. A warmed block allocates nothing: the host reuses each port's message objects
and data views from block to block, so the garbage collector has no churn on the MIDI path.

**Faults.** A node that throws in `process()` faults: the executor silences it and the box prints it once, as for a C++
node. Each `process()` call runs under a deadline enforced by mquickjs's interrupt handler; an overrun is a fault. A pack
whose heap runs out has a dead context, and all of its nodes fault.

**One library, two widths.** The host compiles for x86-64 on the desktop and for the M33 on the box, over the same
stdlib table and the same pack source; only the bytecode's width differs (64-bit on the desktop, `-m32` on the box).

## 5. Memory, the loader and the arena

**Package-level memory.** `rp_package` gains an optional hook: a size and an alignment, and calls to set the package up
in memory the host gives it and to tear it down. A C++ package leaves it unset. A script pack answers with its declared
heap plus its context's fixed overhead.

**The heap** is declared in the pack's manifest (its `package.json`'s `retroplug` field) as a byte count, so the figure
is the same on every host. The desktop's mquickjs host reports a pack's peak use under its tests, so an author sees how
close the declaration is.

**Sizing and placing.** The loader finds the packages the plan's node types come from, sizes each package's memory once
in the same pass that sizes everything else, places it in the arena before the nodes, sets the package up before any of
its nodes is created and tears it down after the last is destroyed. A plan whose packages do not fit is refused naming
the pack and the overrun; the exporter runs the same sizing, so a box plan that cannot fit fails the firmware build.

**The arena** shrinks from 128 KiB toward the box plan's need (the bridge's 30 KiB, plus the `bliptoaster` pack's heap
and context), sized by the prototype's measurement with headroom; about 64 KiB is expected.

**The SRAM budget**, recorded here and in `tools/build-box.sh`'s size line:

| | E3 | E4 (estimate) |
|---|---|---|
| Code and data | about 177 KiB | about 277 KiB (mquickjs about 100 KB, plus the packs' bytecode) |
| Arena | 128 KiB | about 64 KiB, the pack heaps inside it |
| In all | about 305 KiB | about 340 to 390 KiB of 512 |

What remains is recorded for the audio version's buffers.

## 6. `defineNode`, the toolchain and the `bliptoaster` pack

**`defineNode` made portable.** It and its helpers (the `s` schema, the descriptor) are written in the mquickjs subset:
plain objects for Set, loops or local helpers for `includes`, `find`, `Object.entries`, `startsWith`, `endsWith` and
`Number.isInteger`. Desktop packs behave exactly as before, and the descriptor goldens, `buildGraph`'s goldens, the
protocol nodes' recorded digests and parity hold unchanged as the proof.

**Device-pack checks.** For a pack marked for the device, `defineNode` refuses an audio port at definition, naming the
node and the port. A `create()` or `process()` that returns a promise or a thenable faults at its first call.

**The toolchain.** A device pack is bundled by esbuild against a module allowlist, lowered to ES5 by the repo's pinned
TypeScript 5, scanned for library calls mquickjs lacks (a hit fails the build naming the call and its source line), and
compiled by `mqjs` to bytecode: 32-bit for the box, the host's width for the desktop. The steps are `check:portable`'s,
generalised for packs; CMake runs them as `bundles.cmake` runs today's script bundle, and a product that lists a device
pack embeds its bytecode.

**The manifest.** A script pack's `package.json` declares its entry, `device: true` and its heap, and
`cmake/packages.cmake` reads them beside the C++ packs' fields. Products list script packs as they list C++ ones.

**The `bliptoaster` pack** (`packages/bliptoaster`) holds one node, `rp.bliptoaster.midi-policy`, with no settings: it
drops polyphonic and channel aftertouch, system common and realtime, and passes every other message unchanged, its frame,
flags and order kept; its output capacity follows its input's (`capacity.match`). The box's plan becomes
`rp.device.midi-in` -> `rp.bliptoaster.midi-policy` -> `rp.n8.nes`. The desktop products list the pack, so the node can
be auditioned there, and their `[packages]` rows gain it. The desktop's own N8 graphs (`buildGraph`) do not use it in
E4.

## 7. Tests

- **The mquickjs host on the desktop:** a node's lifecycle, settings and block API; each fault (a throw, a deadline
  overrun, a heap that runs out silencing only its pack); a warmed block allocating nothing, counted by the C allocator
  and by the JS heap's growth.
- **`retroplug-device-mode-test`:** the box's plan with the `bliptoaster` pack, exported and loaded into an arena over the
  device-mode builds and run in ragged blocks, renders what GraphHost renders; a pack heap's sizing and its refusals;
  a C++ package without package memory unchanged.
- **The twin test:** `rp.bliptoaster.midi-policy` against `rp.core.midi-filter` with the same kinds dropped, message for
  message.
- **`defineNode` on both engines:** the TS tests on Node, and its helpers run on mquickjs; the toolchain's refusals (a
  missing library call, an audio port on a device pack, an asynchronous `process()`), each with its message.
- **The device builds:** `rp-device-check` runs a script pack through the loader on the device; `device:check` and
  `device:box` link mquickjs under the 87-symbol trap (its `setjmp` and `abort` pass or are wrapped: the prototype
  says which) with `-Werror=stack-usage=1024` on its sources (a frame past the limit takes E3's per-source remedy,
  named in a comment).
- **Held:** parity, the kit and render goldens, the existing descriptor and `buildGraph` goldens, the protocol nodes'
  digests and `edio-golden.json`. The intended changes are the `[packages]` rows gaining `bliptoaster` and the new
  pack's goldens.

## 8. Landing

Five commits, each leaving every suite green:

1. **`defineNode` made portable** and the device-pack toolchain.
2. **mquickjs and the script host** on the desktop, and package-level memory in the SDK and the loader.
3. **The `bliptoaster` pack and the box:** packs embedded and registered at boot, the arena trimmed, the new
   `plan.json`.
4. **`rp-device-check` with a script pack.**
5. **Docs.**

**Acceptance:** every suite with and without the fixtures, parity strict, the kit and render goldens under their
require flags, the sanitizers, `device:check`, `device:box` and the CI dry run, a fresh tree, the live hosts and the
consumers. Then the hardware, by the controller, BlipToaster for every leg: E3's Pico gate with the TS node now on every
message, its latency held to E3's figures (each run's average near 610 to 680 us and worst near 1086 to 1128 us; a worst
above about 1150 us, or averages near 700 us or more, is a regression to report and fix); the console showing the pack's
heap use; and `rp-device-check` flashed once with its script-pack line, then the box flashed back.

**How it is built** (as E1 to E3, Anthropic models only): a verified prototype on the local branch `proto/e4-mqjs`,
stages 1 to 4 by Opus and stage 5 by Sonnet, each reviewed by Opus with a fix pass, the Pico gate run by the controller
on the prototype's image; the plan generated from the prototype, replayed to identical trees and reviewed by Opus;
Sonnet implementers, Opus code reviews, Sonnet acceptance, the controller's hardware legs, an Opus final review. Work
files in the gitignored `.superpowers/e4pro`, `e4plan` and `e4exec`.

## 9. Left beyond E4

- **Packs in plans that are not built in:** a plan on the SD card or a live upload that brings its own packs needs the
  per-node port signature E3 recorded and a trust model for bytecode, which mquickjs does not verify.
- **The desktop's N8 graphs** using `rp.bliptoaster.midi-policy` in place of their own path.
- **`feature/launchpad`** adopting the toolchain for its portable core.
- **The audio version** (E3 section 10), whose RAM this design budgets around.

## 10. Prototype questions

1. mquickjs's code size and RAM on the RP2350, and its stack frames under the 1 KiB limit.
2. The per-message cost of a script node in the MIDI path, and the garbage collector's behaviour with message objects
   reused.
3. Bytecode placement under `copy_to_ram`: mquickjs wants bytecode relocated to the address it runs from; whether the
   build relocates it to its RAM address or the box relocates it at boot.
4. Keeping the stdlib table the bytecode was compiled against equal to the firmware's (mquickjs checks its version, not
   its atoms).
5. The arena's final size, and the pack's real heap use against its declaration.
6. Whether `setjmp`, `longjmp` and `abort` pass the box's link trap as they are, or need wrapping.
