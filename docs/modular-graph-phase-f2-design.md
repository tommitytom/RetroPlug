# Phase F2: the native carve

**Date:** 2026-11-08 · **Branch:** `feature/modularize` · **Status:** designed; not yet prototyped

F2 is the third phase of the package split ([package-split.md](package-split.md)), after F1
([modular-graph-phase-f1-design.md](modular-graph-phase-f1-design.md)) and F3
([modular-graph-phase-f3-design.md](modular-graph-phase-f3-design.md)). F1 gave every cart a TS home and F3 gave the
Launchpad a whole pack; the consoles are the part that is still `packages/native`'s. `rp_sameboy_package`,
`rp_mesen_package` and `rp_host_io_package` are entries of the shell's own manifest, the cores they adapt sit in the shell's
`retroplug-core` library, the engine builds a core through a registry of console backends it names itself, and the Mesen
static library carries every console Mesen ever emulated. F2 carves all of that along the package line: a neutral `system`
package holds the contract, `sameboy` and `mesen` hold their consoles, `host-io` holds the host MIDI nodes, the mGB ROM
becomes a package's embedded resource, and txiki and efsw become libraries a product opts into.

Everything the user approved in the brainstorm is binding here. What the brainstorm left to the prototype is named as such
where it comes up, and listed in section 9. The phase is a carve, not a feature: no audio changes, and the one baseline that
moves is a registration golden, in its own commit (section 8).

## 1. Goal and scope

**Goal.** The packages split's goal, for the native side: each console's code lives in its own package with its dependencies
declared, the engine knows no console, and the boundary checks that already hold the carts hold the consoles. Leaner
products are not the driver; where the carve makes one cheaper (Mesen without the consoles RetroPlug never runs) it is
measured, and nothing is judged by it.

**Scope (one phase, the whole native list).** A neutral native package for the system contract; the `sameboy` and `mesen`
native halves; the C++ closed sets opened and the backends no longer generated by anyone (section 3); a `host-io` package;
the mGB embed seam; Mesen's compile-out per console; txiki and efsw as opt-in shell libraries. It runs as one prototype in
five stages (section 9), the way F3's did.

**Not in F2** (F4's, and recorded in section 10): the TS `Platform` and `Core` unions in `packages/core/ts/platform.ts`
(`gb|nes|gba|sms|gg`, `sameboy|mesen`) and everything that switches on them (`systemRoles`, `constructSpec`, the shell's
`NODE_TYPE`, `projectConfig`'s zod enums, `render.ts`, `menuDefs`); the shell's `loadMgb` and its "an embedded ROM is a Game
Boy" rule; per-product bundles.

## 3. Building a core

**The decision (the user's choice B): the node builds its own core through its package's build function, carried in the
request.** The registry of backends the engine kept goes; the engine keeps the bookkeeping.

```cpp
// system/SystemBuild.hpp (in the `system` package)
struct SystemBuildRequest;

using SystemBuildFn = std::unique_ptr<SystemBase> (*)(SystemId id, SystemBuildRequest&& request, double sampleRate,
                                                      std::string* why);

struct SystemBuildRequest {
    std::vector<std::uint8_t> rom;
    std::vector<std::uint8_t> sram;       // battery RAM seed (may be empty)
    std::vector<std::uint8_t> savestate;  // savestate seed (may be empty)
    std::string               romName;    // as today: the ROM's file stem
    std::uint32_t             maxBlockFrames = 0;
    SystemBuildFn             build = nullptr;      // the node's package's: how this request becomes a core
    const void*               config = nullptr;     // the node's console config, which only `build` reads
};
```

The request keeps today's fields (`SystemBuildRequest` in `system/SystemFactory.hpp`, with the same comments) and replaces
`SystemConfig config` with the pair above. `config` points at the console config the node's settings made (a `SameBoyConfig`,
a `MesenNesConfig`), living in the node for the duration of the call; `Engine::buildSystem` calls `build` synchronously on the
control thread inside the `setGraph` that activates the node, so the pointer never outlives its owner. A build function is a
plain function (no captures: the node's type names it), which is why it is a function pointer. Its `why` is the same
out-parameter the backends use, and it consumes the request, as `SystemBackend::build` did, so the ROM is moved into the core
rather than copied.

**`rp.host.systems/1` becomes `/2`.** The `HostSystems` struct keeps its `build` and `destroy` members and their shapes; the
id moves because the request a node hands across it changed layout (a node built against `/1` would read the config as a
variant). Every consumer is in tree (the system nodes, `NodeRig`), as with C5's `rp.host.devices/2` and the engine host I/O's
`/3`. `HostSystems` and `EngineSyncTrace` move to the `system` package (the nodes bind them; the engine implements them); the
`EngineHostIo` half of `HostServices.hpp` goes to `host-io`.

**`Engine::buildSystem` keeps its checks and their order,** and calls `request.build` where it called the factory:

1. a system is built only inside the `setGraph` that activates it (`building_`);
2. 0 is not a system id;
3. the id is beyond a system id (above `UINT32_MAX`);
4. the id is live (`coreLive`), held by a node of any plan not yet reclaimed;
5. **new:** the request names no build function, refused with its own reason before anything is claimed;
6. `request.build` runs, and a null core is refused with its reason (or "the core did not build");
7. the snapshot slot is claimed (a full pool refuses, after the build has paid for it, as today);
8. the plan's slot for the id is filled, or the core is destroyed and the build refused.

Nothing else in `buildSystem` changes: the core is still the node's until `destroy`, the live-core table and the registry
still hold it, and `destroySystem` is untouched.

**Recognising a system node.** `isSystemNodeType` (`Engine.cpp:81`) walks two packages by name today, which is the engine's
last edge to a console. It becomes the registered type's descriptor: a node type is a system node when its descriptor's
`category` is `"system"`. Every system node already declares it (`static constexpr const char* category = "system"` in the
four node classes, and no other C++ node type uses the word; the descriptor carries it as `put(o, "category", ...)` in
`Descriptor.cpp`), and the engine reads it from the `NodeRegistry` entry it already holds for the planner. No ABI change.
The use at `Engine.cpp:383`, which lines `sys-<id>` nodes up against the plan's slots, is unchanged.

## 4. Mesen's per-console compile-out

**The decision (the user's choice A).** The Mesen library stops carrying consoles RetroPlug never runs, by an option per
console, not a new library and not a patch series.

- **Options.** `MESEN_ENABLE_SNES`, `MESEN_ENABLE_PCE` and `MESEN_ENABLE_WS`, declared in `deps/mesen/CMakeLists.txt`,
  **default ON** (upstream's behaviour, so the vendored directory still builds as Mesen), and set **OFF** by the root
  `CMakeLists.txt` before `add_subdirectory(deps/mesen)`. `SNES` covers the Game Boy core too: the two are coupled through
  Super Game Boy (SNES constructs a Game Boy, and the Game Boy's SGB support calls into SNES), so one switch drops both.
  NES, GBA and SMS are always built (the SNES's ST018 coprocessor borrows the GBA's ARM core; that edge leaves with the
  SNES, and GBA itself reaches no other console). Each option is a PUBLIC compile definition of the `mesen` target, so the
  translation units that include Mesen's headers see the same guards the library was built with.
- **The filter.** Next to the existing `list(FILTER ... EXCLUDE)` calls: drop `Core/<Dir>/` for each disabled console, and the
  per-CPU `Core/Debugger/ExpressionEvaluator.<Cpu>.cpp` files of its CPUs (the Snes, Spc, Gsu, Cx4, NecDsp, St018 and
  Gameboy evaluators for SNES; Pce; Ws; the Nes, Gba and Sms ones stay). It is written as a table of console, directory and
  evaluators, so a further switch is one more row. **Two SNES shim translation units are kept:** `SNES/Input/SnesController.cpp`
  (the input hub, the four-score and the NES control manager construct it) and `SNES/SnesDefaultVideoFilter.cpp`
  (`Emulator::GetVideoFilter`'s fallback). Only `.cpp` files are filtered; headers stay on disk, so every `#include` keeps
  compiling and only a call or construction into a dropped unit needs a guard.
- **The guards.** `#if MESEN_ENABLE_*` around the references into dropped code, each marked `// RetroPlug:` as the 42 files
  already patched in the vendored tree are (the tree has no `.git` of its own, upstream is SourMesen/Mesen2 at `b9fa69d`, and
  there is no `RETROPLUG_` macro in it today). About 300 mechanical lines in `Core/Shared/Emulator.cpp` (`TryLoadRom<X>`,
  about 4 lines), `Core/Debugger/Debugger.cpp` (19 switches, the new-debugger runtime switch and the explicit instantiations,
  about 120 to 150), `MemoryDumper.cpp` (about 60), `DisassemblyInfo.cpp` (about 70), `Disassembler.cpp` (about 20) and
  `ExpressionEvaluator.cpp` (the token switches, about 16). Counts are the survey's estimates; the prototype's diff is the
  record.
- **What stays whole:** the debugger (the NES debug session needs it), and with it Lua (`ScriptManager`) and netplay (the
  `Emulator` constructs `GameServer` and `GameClient`). The cut is about 138 of 426 translation units and 12 MB of 31 MB of
  objects (39%), with a proportional share of the LTO link.
- **The risk the guards carry.** A plain `switch` over a template parameter references every arm at `-O0`, so a missed guard
  links under Release and fails under Debug. That is why the proof below builds Debug.
- **Two-way proof.** (1) The dev loop's build, with the root's options OFF, in Release, in Debug at `-O0`, and in Release with
  `RETROPLUG_MESEN_LTO=ON` through the link; with `nm` on the product finding no `SnesPpu`, `GbPpu`, `PceVdc` or `WsPpu`.
  (2) A separate build directory with all three options ON, which must compile (and link a product), so the guards cannot
  rot into a build that only works with the options off. A configure or build check that an enabled build still compiles holds
  the second; where it runs (a script, a CI job) is the plan's.
- **Measurements, recorded and not gated:** the mesen library's object bytes before and after, its compile time, the product
  binaries' sizes, and one Release plus LTO link time.
- **Stale comments fixed in the same stage:** `deps/mesen/CMakeLists.txt`'s header (the linker does not drop what is
  unreferenced, and the "deferred to a later pass" is this pass); `AGENTS.md`'s "one parallel-cores fix" (the vendored tree
  carries 42 files with `// RetroPlug:` markers, `SimpleLock` is one of them); and the "nine binaries linking" count wherever
  it is repeated.

## 5. Embedded resources

The mGB ROM stops being a closed `id == "mgb"` in a header the shell owns and becomes a package's declared resource.

- **The manifest member.** A package's `retroplug` field may have `embed: [{ "id": "mgb", "file": "rom/mGB.gb" }]`. `id` is a C
  identifier (it names the generated array) and `file` is a path inside the package, so `packages/mgb/rom/mGB.gb`.
  `cmake/packages.cmake`'s manifest reader accepts and validates the member; a package that has only an `embed` member is
  still a package with a contribution to read.
- **The generated table.** For each package with an `embed` member `retroplug_package` adds an object library
  `retroplug-<package>-embeds`, built through `cmake/bin2c.cmake` (the script the root target used) into one array per entry.
  `retroplug_product` generates `rp_embedded_resources()` for the product, a table from id to bytes over the product's
  packages, and the shell declares it beside `rp_register_packages`. `EngineRpcService::putResource` looks up the table in
  place of `rp::embeddedRom`. A product that does not list `mgb` has no `"mgb"` in its table, so the lookup refuses it.
- **Refusals.** An id that is not in the table is refused with today's words (`"<id>" is not an embedded ROM`); a
  duplicate id across the product's packages is refused at configure (the generator names both packages); an entry whose
  `file` resolves outside the package, or does not exist, is refused at configure. Configure fixtures hold the last two
  the way `test/packages/refused` holds the manifest rules.
- **The wire does not change.** `BackendResourceSpec{type, bytes?, path?, embedded?}` and the TS that sends
  `embedded: "mgb"` are as they are. `EmbeddedRoms.hpp`, `mgb_rom` / `mgb_rom_len` and the root `mgb-rom` target go. The TS
  chain (the menu's `start-mgb`, the stores' `loadMgb` going through `loadInPlace("", "mgb")`, `embedded` meaning platform
  `gb`, the persisted `embeddedRom`, the CLI SDK's `loadMgb` and about twenty `test-native` suites) stays exactly as it is;
  it is the shell's and F4's.
- **The stale comments** that name `SameBoyBackend` as the resolver are corrected where they stand.

## 6. txiki and efsw

Two shell libraries, each linked by the products that use it (the user's choice A). Neither is a package: both are the
shell's, since they serve the hosts and not a console.

- **`retroplug-tjs-runtime`** compiles dpf.js's `TjsHostRuntime.cpp` and links `tjs` (which brings `qjs` and libuv). Its
  users are the products that run the control plane on txiki: the headless host, the CLI, the SDL standalone, the plugin
  and `retroplug-classid-test`. `QuickJsGlobals.hpp` and `GamepadPump.hpp` include `TjsHostRuntime.hpp` only for the
  QuickJS types they use and are reduced to what they need (`quickjs.h`), splitting `QuickJsGlobals.hpp` if one of its
  pieces needs the runtime class and another does not.
- **`retroplug-file-watcher`** compiles `NativeFileWatcher.cpp` and links `efsw-static`. `HostRpcService` holds a
  `FileWatcher` interface (the two calls it forwards, `drainChangedPaths` and `setWatchedRoms`) instead of a
  `NativeFileWatcher`, and `enableWatching` takes the watcher: `enableWatching(std::unique_ptr<FileWatcher>)`. The plugin
  builds a `NativeFileWatcher` and passes it; every other host passes none, as today. `retroplug-watcher-test` links the
  library.
- **The backend links `qjs`, not `tjs`.** The script host, the render host and the compiler are bare QuickJS, and
  `RenderHost.cpp`'s include of `host/QuickJsGlobals.hpp` (which pulls `TjsHostRuntime.hpp`) is unused by it and goes, so
  the Node addon, `retroplug-render-host-test` and the engine tests no longer carry txiki's host or efsw.
- **A configure check** (`retroplug_check_runtime_libraries`, beside `retroplug_check_products`) refuses a configure in
  which the Node addon, `retroplug-render-host-test`, `retroplug-backend`, `retroplug-engine-graph-test` or
  `retroplug-audio-test` carries `tjs`, `uv_a` or `efsw` in its link closure, with the target and the library named. A fixture
  holds it the way F1's fixtures hold the boundary checks: a scratch binary that links one must be refused.
- **The two `EXEMPT` tests are re-examined.** `retroplug_check_products(LIBRARIES retroplug-backend EXEMPT
  retroplug-classid-test retroplug-watcher-test)` exempts the two binaries that link the backend for what is no longer in
  it. Once they link `retroplug-tjs-runtime` and `retroplug-file-watcher` instead, whether either stays exempt (it still
  never pulls the engine's object in) or becomes an ordinary product is settled by the check's own result.

## 7. The boundary check's new cases

The native boundary check (`cmake/packages.cmake`, `_retroplug_check_native_boundaries`; F1 section 4) judges every target
whose source directory is a package's. F2 adds four packages' worth of targets (`retroplug-system`, `retroplug-sameboy`,
`retroplug-mesen`, `retroplug-host-io`) and the rules they meet:

- **Declared dependencies are the edges.** `sameboy`, `mesen` and `host-io` declare `system` (or `node-sdk`) in their
  `package.json`; `mesen` declares `n8`. A target that links or includes a package's tree without declaring it is refused,
  as for any pack. The check allows `node-sdk` to every package already.
- **No genexes to avoid.** The check judges only `$<BUILD_INTERFACE:>`, `$<LINK_ONLY:>` and `$<TARGET_NAME:>` and refuses any
  other form as unjudged. Two of `retroplug-core`'s links are such forms and would be refused if moved as written:
  `$<$<BOOL:${WIN32}>:retroplug-samebsys>` becomes an `if(WIN32)` in the `sameboy` package's CMake, and
  `$<TARGET_PROPERTY:retroplug-n8,INTERFACE_INCLUDE_DIRECTORIES>` becomes a link to `retroplug-n8` itself, `mesen`'s declared
  dependency. The DSP-header one (`util/Hash.hpp`) is `SampleCache`'s alone, which stays in the shell.
- **The clang-cl custom command.** On Windows `SameBoySystem.cpp` is compiled by `clang-cl` in a custom command (it pokes
  SameBoy internals `cl.exe` cannot parse) into a static library. It moves into `packages/sameboy/native/CMakeLists.txt`
  behind `if(WIN32)`, with its hard-coded `packages/native/src` paths rewritten to the package's, `system`'s and the node
  SDK's directories alone (its include roots reach the SDK for `util/FixedQueue.hpp` and the generated and reflect-cpp
  directories), its header glob over those same directories and its `DEPENDS` on the boot-ROM target. The check does not read
  a custom command's command line (its header already lists what it does not look at); the command's dependency list and
  its three include roots are held by being written against the package's own directories, and the rewritten command is
  owed a Windows run (section 8).
- **Fixtures.** The existing `check-native-boundaries.cmake` fixtures gain two: a mesen-shaped scratch package that reaches
  `n8` without declaring it must be refused, and a `system`-shaped one that reaches the shell must be refused; a scratch
  package that declares what it reaches must hold. The warnings list (`packages/native/cmake/warnings.cmake`) puts `/W4 /WX` on the new
  targets, which the Windows rules of `AGENTS.md` then apply to.

## 10. What it leaves

- **`MemoryType`** stays a closed wire enum of nine regions. A package that wanted a tenth would change the wire, the debug
  RPCs and the TS mirror together; there is no such package, and the enum is not a build seam.
- **The TS unions.** `Platform` and `Core` in `packages/core/ts/platform.ts`, `NODE_TYPE`, `projectConfig`'s zod enums, the
  literal switches in `render.ts`, `menuDefs`, the cli render session and `buildGraph`, and the generator's closed
  `NODE_KEYS` are F4's.
- **`loadMgb` and "an embedded ROM is a Game Boy"** stay in the shell's stores and the CLI SDK until F4. The embed seam gives
  the native side a table; the TS still knows `"mgb"` by name.
- **Mesen on an N8 as a cart seam.** `mesen` declares `n8` because `NesN8FifoRole` includes its reliable-link header, which
  is the smaller edge. A later change could make the emulated N8 FIFO a cart the N8 pack offers through a link interface
  and take the include out of `mesen` (option B in the brainstorm); it is not part of F2.
- **Per-product Mesen consoles.** The compile-out is one library for every product, with the root's options. A product that
  wants fewer consoles, or an embedder who wants SNES back, flips an option; making that a per-product choice (a Mesen
  library per console set) is a later question the filter's table is written to make cheap.
- **A Windows run.** The new targets, the moved clang-cl step and the Mesen options have been reasoned about and never run
  on MSVC; the first run is the user's Windows agent's, and findings become follow-ups.
- **Per-product bundles** (the render worker, script nodes and control-plane bundles embedded in every product) are F4's.
